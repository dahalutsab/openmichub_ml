OpenMicHub Teardown

The architecture is sound and the feature surface is genuinely ambitious — bookings, payments, an earnings wallet, chat, a social feed, an LLM assistant. But the app does not start on Linux or macOS, and the money layer can be drained by anyone with curl and no account. Everything marked proven below I reproduced on a live instance.

The blocker — fixed, one character

application-local.yml pointed at certs/public_Key.pem. The file on disk is public_key.pem. Windows didn't care; Linux and macOS refuse to boot the context at all — RSAKeyRecord fails to bind and the whole app dies at startup.

I changed the capital K to lowercase in src/main/resources/application-local.yml:33. That is the only source edit I made. The app now starts clean and Hibernate builds the full schema.

The money layer

This is where the serious problems are. The payment callback is the front door and it is unlocked, and the wallet arithmetic behind it is wrong in a way that destroys data.

Critical Proven live PAY-01

Anyone can mark any payment "Completed" without paying

SecurityConfig.java:54 · PaymentServiceImpl.java:200–209

/api/v1/payments/callback is permitAll(), and it trusts the status and amount query parameters it is handed. Khalti is never called back to verify the transaction — there is no lookup request anywhere in the codebase. The Angular PaymentCallbackComponent simply forwards whatever query string lands in the browser, which means the "proof of payment" is attacker-controlled by design.

Unauthenticated request against a running instance
$ curl -X POST "localhost:8181/api/v1/payments/callback\
?pidx=FORGEDPIDX123&status=Completed&amount=1&totalAmount=1"

Payment processed successfully   HTTP 200

payment  → FORGEDPIDX123 | COMPLETED | received_amount 0.01
wallet   → balance 3800.00   (paid: one paisa)
Fix Call Khalti's epayment/lookup/ with the pidx and trust only that response. Compare the returned amount against the stored Payment before crediting anything. Keep the endpoint public (gateways need it) but treat every parameter on it as hostile.
Critical Proven live PAY-02

Every completed payment erases the artist's entire balance

VirtualCoinServiceImpl.java:40 · PaymentServiceImpl.java:227–246

createOrUpdateVirtualCoin() does setBalance(request.getBalance()) — it assigns rather than adds. handleCallback calls it with the amount for this one booking, so the artist's accumulated earnings are overwritten by a single booking's value. Then createTransaction() runs and adds the same amount again, so the number that lands is double one booking and bears no relation to what the artist actually earned.

Artist with existing earnings receives one new 2,000 booking
balance before   50000.00
                 ↓ one payment callback for a 2,000 booking
balance after    3800.00   ← 48,100 in earnings destroyed

   assign 1900 (overwrite)  +  add 1900 (transaction)  =  3800
Fix Delete the balance write from createOrUpdateVirtualCoin entirely. Let createTransaction be the single place that moves the balance, and derive the balance from the transaction ledger rather than storing it as an independently mutable column.
Critical Proven live PAY-03

Callbacks are replayable — no idempotency key

PaymentServiceImpl.java:200

Nothing checks whether a pidx has already been processed. Firing the identical callback twice produced two APPROVED credit transactions of 1,900 each against one booking. The ledger and the balance column drift apart immediately, and there is no reconciliation job to catch it.

Fix Return early when payment.getPaymentStatus() is already COMPLETED. Add a unique constraint on payment.pidx, and a unique constraint on (booking_id, transaction_purpose) for booking credits.
Critical PAY-04

The payout endpoint is public and doesn't check who owns the transaction

SecurityConfig.java:55 · BookingController.java:103 · BookingServiceImpl (withdraw)

/api/v1/artist/withdraw is permitAll(). It takes a transactionId from the request body, looks it up, and initiates a real Khalti payout — without checking that the caller is the artist who owns it, that the caller is authenticated at all, or that the transaction is still PENDING. Transaction IDs are sequential. /api/v1/artist/withdraw/callback is whitelisted and unverified on the same pattern.

Fix Require authentication, resolve the artist from the security context (never from the request), and assert transaction.virtualCoin.artist == loggedInArtist plus status == PENDING before initiating anything.
High PAY-05

Withdrawal requests never reserve the balance

TransactionServiceImpl.java (withDraw)

withDraw() checks the balance, then writes a PENDING debit — but never deducts or reserves anything. An artist with 1,000 can submit fifty separate 1,000 withdrawal requests and every one passes the check. The balance is only reduced later, in the withdraw callback, once per approval.

Fix Deduct into a held/pending balance at request time and release it if the payout is declined, or compute available balance as balance − sum(pending debits) in the check.
High PAY-06

Bookings are never confirmed after successful payment

PaymentServiceImpl.java:209–250

The success branch updates the payment, the wallet and the ledger, but never touches booking.status — it stays PENDING forever. The code that would have set CONFIRMED / CANCELLED is sitting commented out in the failure branch. Users pay and the booking still looks unconfirmed.

Medium PAY-07

Sub-hour and partial-hour bookings are billed wrong or crash

BookingServiceImpl / PaymentServiceImpl — Duration.between(...).toHours()

toHours() truncates. A 90-minute booking bills one hour. A 45-minute booking computes a total of zero, which then throws "Received amount must be greater than zero" and the user cannot pay at all.

Fix Use Duration.toMinutes() / 60.0, and move all currency off double onto BigDecimal — every amount in the system is currently a float.
Medium PAY-08

@Transactional on a method returning Mono does nothing

PaymentServiceImpl.bookArtist · BookingServiceImpl.withdraw

Both methods are annotated @Transactional but return a Mono. The transaction commits when the method returns the publisher — before doOnNext ever runs. The paymentRepository.save() inside doOnNext executes on a Reactor scheduler thread outside any transaction and outside the request's persistence context. If Khalti is slow or the subscriber goes away, the payment row is silently never written.

Authentication & access control

There is a role model in the database — ADMIN, USER, ARTIST — and nothing in the application consults it.

Critical Proven live AUTH-01

No authorization exists anywhere in the codebase

Whole service — grep -r "PreAuthorize|hasRole|hasAuthority" returns nothing

@EnableMethodSecurity is switched on in SecurityConfig, but there is not a single @PreAuthorize, @Secured or hasRole() in the project. Every authenticated account — including a freshly registered end user — has identical access to every endpoint, including the admin surface.

Requests made with a plain USER token
GET /api/v1/user/all        → 200  full user directory, emails, roles
GET /api/v1/payments        → 200  every payment on the platform
GET /api/v1/transactions    → 200  every artist's earnings ledger

(anonymous requests correctly return 401 — the gap is role separation)
Fix Annotate the admin surface with @PreAuthorize("hasRole('ADMIN')") and the artist surface with hasRole('ARTIST'). Also fix JwtTokenGenerator.getPermissionsFromRoles(), which checks for ROLE_SCHOOL_ADMIN — copy-paste from a different project, so the scope claim it builds is meaningless for every real role.
Critical AUTH-02

Access tokens are encrypted but never signed

JwtTokenGenerator.java · JwtAccessTokenFilter.java

Tokens are JWE objects built with RSA_OAEP_256 using the public key, and the filter decrypts them with the private key and accepts the claims. There is no signature step at any point. Encryption proves confidentiality, not authorship — anyone holding the public key can encrypt a payload of their choosing, and the server will decrypt it and trust the sub claim. The public key is committed to the repository.

Fix Sign first, then encrypt: build a SignedJWT (RS256, private key), wrap it in the JWE, and have the filter verify the signature after decrypting. Or drop the JWE and use plain signed JWTs, which is what the oauth2-resource-server dependency already on the classpath expects.
Critical AUTH-03

Password reset OTPs aren't bound to a user and can be brute-forced

OTPServiceImplementation.java:49 · AuthServiceImpl.resetPassword

getOTP() looks up by findByOtpValueAndPurpose(otp, purpose) — value and purpose only, no user. resetPassword takes whatever user that row happens to belong to and changes their password. The OTP is six digits, there is no rate limiting, no attempt counter, and no lockout. An attacker walks the keyspace and resets a stranger's password — they don't get to choose whose, but with any real user base that hardly matters.

Separately, isUsed is written on the entity but never checked, so a reset token stays valid for its full five-minute window no matter how many times it has been redeemed.

Fix Use a long random token (not a 6-digit code) for password reset links, scope the lookup to the user, check isUsed, and add per-IP and per-account rate limiting on /forgot-password and /reset-password.
High AUTH-04

Email verification is never enforced at login

AuthServiceImpl.getJwtTokensAfterAuthentication

UserEntity.verified is set to false at registration and checked nowhere in the login path. Unverified accounts log in and receive a full token, which makes the entire OTP registration flow decorative.

High AUTH-05

Insecure direct object references across four domains

BookingServiceImpl · PostServiceImpl · ReviewServiceImpl

None of these check that the caller owns the object they are mutating. Any authenticated user can approve or decline anyone's booking by ID (approveBooking, declineBooking), edit or delete anyone's post (updatePost, deletePost) and edit or delete anyone's review (updateReview, deleteReview).

createReview additionally never verifies that the reviewer booked that artist, that the booking is complete, or that they haven't already reviewed it — so artist ratings can be set by anyone, repeatedly.

High AUTH-06

Artist earnings ledger leaks to other artists on an empty result

TransactionServiceImpl.getAllLoggedInArtistTransaction

The query falls back with .orElseGet(() -> transactionRepository.findAll(pageable)) — when an artist has no matching transactions, the response is every transaction on the platform. Related: the ALL enum member is passed straight into a findAllBy…TransactionType… query, so filtering by "ALL" matches literal ALL rows and returns nothing instead of everything.

High AUTH-07

Uploaded file extensions are taken raw from the client

FileHandlerUtil.saveFile / getFileExtension

The base name is sanitized, the extension is not — it is sliced off the client-supplied filename and concatenated straight into the path. A crafted filename traverses out of the upload directory, and because /media/** is a public static resource handler, anything that lands there is served back. Content type is never validated against magic bytes, only the extension string.

Medium AUTH-08

CORS reflects any origin with credentials enabled

CorsConfig.java

addAllowedOriginPattern("*") together with setAllowCredentials(true) means every origin on the internet is echoed back as allowed. Pin this to the actual frontend origins per environment.

Medium AUTH-09

Token lifetime is advertised as 15 minutes and is actually 150

JwtTokenGenerator (150 min) vs AuthResponse accessTokenExpiry(15 * 60)

The frontend is told 900 seconds; the token lives two and a half hours. There is also no refresh token despite the Swagger description promising one, no revocation list, and logout only clears the Angular localStorage entry — a stolen token stays valid for its full life.

Committed secrets

Four live credentials are in the working tree. Treat all of them as burned and rotate them — redacted here, but they are in plaintext in the repo.

Medium SEC-02

Seeded admin uses a published default password

InsertInitialUserInfo.java

admin@openmichub.com / Admin@123 is created on every boot and hardcoded in source. I logged in with it on the instance I ran. Seed from an environment variable and force a password change on first login.

Features that don't work

Built, wired to the UI, and non-functional at runtime.

High Proven live FN-01

Chat messages are never saved — history is permanently empty

WSMessageController.sendPrivateMessage

The handler looks up sender and recipient, builds a ChatResponse, broadcasts it over STOMP — and never persists it. The comment says "Save message to database (assuming this is handled elsewhere)"; it isn't. chatRepository.save() does not appear anywhere in the codebase. Messages exist only for connected sockets. getAllChats() and getMyChats() read from a table nothing writes to, so every conversation reloads blank.

Fix Persist a Chat entity in the handler before broadcasting. While you're there: getMyChats returns one row per message rather than per conversation, so the chat list shows the same person repeatedly.
High FN-02

Nothing prevents double-booking an artist

BookingServiceImpl.bookArtist

The booking path checks the artist's weekly availability window and stops there. It never queries existing bookings for that date and time, so the same artist can be booked by ten different organizers for the same Saturday evening. BookingRepository has no method to support such a check.

ArtistUnavailability — the blackout-dates feature — is fully built with an entity, repository, controller and CRUD service, and bookArtist never reads it. Artists can mark themselves unavailable and still be booked.

Medium FN-03

Withdrawal approvals have no admin workflow

withDraw() writes a PENDING transaction and logs "Withdrawal request sent to super admin for approval" — but no notification is sent, and no endpoint exists for an admin to list or approve pending withdrawals. The status is set and never read.

Medium FN-04

Contacts list is filtered after pagination

ChatServiceImplementation.getAllContacts

Inactive and unverified users are filtered out of the page after the database has already paginated, then re-wrapped with the original totalElements. Pages come back inconsistently sized and the total is wrong. Push the predicate into the query.

Medium FN-05

Upload directory is hardcoded to a path that won't exist

FileConfig.java · application-local.yml

On Linux the file root is /home/ubuntu/open_mic_hub/. On your machine — and any dev machine whose user isn't ubuntu — every upload fails on directory creation. Make it one configurable property with a sensible relative default.

Medium FN-06

Spring Security's AccessDeniedException is never handled

GlobalExceptionHandler.java

The handler imports java.nio.file.AccessDeniedException instead of org.springframework.security.access.AccessDeniedException, so authorization failures fall through to the catch-all and return 500 instead of 403. The catch-all also returns raw e.getMessage() to the client, leaking internals.

Medium FN-07

assert is used for a null check

TransactionServiceImpl.createTransaction

bookingRepository.findById(...).orElse(null) followed by assert booking != null. Assertions are disabled by default in the JVM, so this is a plain NullPointerException in production. Withdrawal and service-fee transactions also require a booking ID they conceptually shouldn't need.

What's missing

Not bugs — capabilities a booking marketplace needs that aren't there yet, roughly in the order I'd add them.

  • SchemaDatabase migrations. ddl-auto: update is the only schema management. It cannot drop or alter columns safely and will diverge across environments. Adopt Flyway before there is production data.
  • MoneyRefunds and cancellation. BookingStatus.CANCELLED exists as an enum value with no path to it. There is no refund flow, no cancellation policy, and no way to reverse a credited wallet balance.
  • MoneyReconciliation. Wallet balance is a mutable column that can silently disagree with the transaction ledger. A scheduled job that recomputes and alerts on drift would have caught PAY-02 immediately.
  • SecurityRate limiting. Nothing throttles login, OTP verification, password reset, or the LLM chat endpoint — which is public and spends your API quota.
  • SecurityRefresh tokens and revocation. A single long-lived access token with no server-side invalidation. Logout is client-side only.
  • ProductNotifications. Everything is email. No in-app notification entity, no unread state, no delivery for booking status changes or new messages while offline.
  • ProductArtist discovery. No search, genre filter, location filter, price range, or sort by rating on the public artist listing — the core browsing experience of the product.
  • ProductBooking lifecycle. No COMPLETED state after the event, which is what should gate reviews and release held funds to the artist.
  • QualityTests. One file, contextLoads(), and it currently fails on any machine without the key-casing fix. The payment and wallet arithmetic in particular needs unit tests.
  • OpsNo Dockerfile, no CI, no health checks. Add a multi-stage build for the service, wire the compose file below into it, and run the build on every push.
  • BuildLombok version conflict. pom.xml declares the dependency at 1.18.38 but pins the annotation processor path to ${lombok.version} = 1.18.34. Also mvnw is not executable and maven-wrapper.jar is gitignored, so the wrapper doesn't work on clone.
  • Frontend401 sends users to the register page. AuthInterceptor navigates to /auth/register on any 401 instead of login, and no expiry check happens before requests fire. Tokens live in localStorage, so any XSS is a full account takeover.

Running it locally

You have no local Postgres and your only JDK is 25, which Lombok can't process. Both are solved with Docker — this is exactly how I ran the instance used for the evidence above.

1

Start Postgres. docker-compose.yml is already written at the repo root, matching the credentials in application-local.yml.

cd /devdata/projects/brogrammers/openmichub
docker compose up -d          # postgres 16 on :5432
2

Run the service through a JDK 21 container. The named volume caches ~/.m2 so subsequent starts are fast.

docker run --rm --network host \
  -v "$PWD/open_mic_hub_service":/app \
  -v openmichub_m2:/root/.m2 -w /app \
  maven:3.9-eclipse-temurin-21 mvn spring-boot:run
3

Frontend as usual — it already points at localhost:8181.

cd open_mic_hub_ui && npm install && npm start

Swagger comes up at localhost:8181/v1/swagger. If you'd rather build natively, installing jdk21-openjdk and selecting it with archlinux-java set java-21-openjdk also works — Lombok 1.18.38 supports up to Java 23.
